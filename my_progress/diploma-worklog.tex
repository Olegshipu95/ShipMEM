\section{Постановка}

\subsection{Кратко о задаче}

Сторона кода в PGO изучена хорошо, сторона данных почти нет. Цель проекта: инструмент, который по аппаратным профилям обращений к памяти (PEBS или аналог) автоматически:

\begin{itemize}
    \item разделяет горячие и холодные поля структур;
    \item переупорядочивает члены структур;
    \item меняет размещение объектов при выделении памяти,
\end{itemize}

чтобы working set занимал меньше кеш-линий и страниц.

\subsection{Контекст}

PGO, BOLT и Propeller переставляют код: функции, базовые блоки, горячие/холодные части. Data layout при этом остаётся таким, каким его написал программист. 

Порядок полей определяется читаемостью, а не частотой обращений, а горячие и холодные объекты одного типа лежат вперемешку. При этом механизмы аппаратного сэмплирования (Intel PEBS, AMD IBS) умеют давать адреса обращений к данным, то есть исходные данные для такой оптимизации есть.

\subsection{Исследовательская сложность}

\begin{itemize}
    \item Профиль выборочный и неполный: часть полей и объектов в нём просто не встретится.
    \item Язык позволяет брать адреса данных, есть offsetof, касты, сериализация через memcpy, ограничения ABI. Поэтому нужно доказывать, что преобразование безопасно, а не просто выгодно.
    \item Нужно подтвердить, что перезапись сохраняет семантику программы.
\end{itemize}

\subsection{Возможный план}

\begin{enumerate}
    \item Изучить предшествующие попытки, прежде всего GCC -fipa-struct-reorg и -fipa-reorder-fields, и разобраться, почему struct-reorg из GCC убрали: какие проблемы безопасности или поддержки не удалось решить.
    \item Собрать профили обращений к памяти (perf mem, perf c2c, PEBS/IBS) и сопоставить адреса с полями структур через отладочную информацию.
    \item Определить класс безопасных преобразований и анализ, который их
        разрешает: escape analysis, отсутствие взятия адреса, отсутствие внешней
        видимости типа.
    \item Реализовать преобразования: переупорядочивание полей, hot/cold splitting структур, раздельные арены для горячих и холодных аллокаций. Здесь стоит опереться на существующие hot/cold hints для аллокаторов: operator new с hot/cold hint в tcmalloc и LLVM MemProf, который расставляет такие hints по профилю.
    \item Измерить эффект: cache-miss, TLB-miss, задержка/пропускная способность на реальных нагрузках.
\end{enumerate}


\subsection{Ожидаемый результат:}

    \item Анализ безопасности преобразований и его ограничения.

\subsubsection{Фаза 2. От адреса к полю}

После получения адресов, необходимо осознать, как адрес из профиля можно
превратить в поле. Далее нагенеренное чтиво, по которому необходимо разобраться: 


\begin{ai}
\begin{itemize}
    \item В DWARF беру тег члена, его смещение и location lists. \\
    Тег называется \texttt{DW\_TAG\_member}. Дамп смотрю командой
    \texttt{llvm-dwarfdump}.
    \item LLVM, Source Level Debugging:
    \url{https://llvm.org/docs/SourceLevelDebugging.html}.
    В IR имя поля лежит в debug info, не в типе инструкции.
    \item \texttt{DataLayout} в LLVM: размеры типов, alignment и
    endianness для x86-64. По ним смещение в байтах становится
    конкретным полем.
\end{itemize}

Два разных случая.

\begin{itemize}
    \item Глобал: символ плюс смещение, дальше запись поля в DWARF.
    \item Куча: база объекта из сэмпла неизвестна. Нужен перехват
    аллокации с типом (обёртка аллокатора или пометка в Clang).
    Иначе адрес не к чему привязать. Стек и location lists --- после
    кучи и глобалов.
\end{itemize}

Дальше считаю частоту поля и совместный доступ: граф близости из
фазы 0.

Clang опускает поле в смещение двумя конструкциями IR.
Сначала \texttt{StructType}, затем \texttt{getelementptr}.
После SROA и mem2reg
структура часто уже разобрана на скаляры, поэтому имя поля в
инструкции не остаётся: оно живёт в debug info и в AST. Полный курс
SSA к таблице полей не нужен. Справочник по конкретной инструкции
LLVM открываю по ходу, Language Reference целиком не читаю.

\end{ai}

\subsubsection{Фаза 3. Безопасные преобразования}

Проблема преобразований стоит явно, ведь непонятно, как доказать их корректность
после оптимизаций. 

\begin{ai}

\begin{itemize}
    \item System V AMD64 ABI, раздел про aggregates: alignment,
    padding, как структуру передают в вызов.
    \item Itanium C++ ABI, глава 2. Clang на Linux кладёт объекты по
    ней: vptr, базы, виртуальные базы. vptr остаётся в начале
    объекта.
    \item Hagog, Tice. \textit{Cache Aware Data Layout Reorganization
    Optimization in GCC}. GCC Summit 2005. Когда reorder и split
    запрещены: address-taken, \texttt{volatile}, внешний ABI,
    битовые поля, union. Это разбор того, что в фазе 0 осталось
    списком отказов GCC.
\end{itemize}

Анализ, который разрешает преобразование, --- escape analysis:
адрес поля не уходит из модуля, тип не виден снаружи. Alias analysis
LLVM открываю только на этот вопрос. TBAA отвечает за strict
aliasing, к горячим и холодным полям он не относится. Вывод Hundt из
фазы 0 применяю к конкретному типу: публичный тип остаётся
рекомендацией.

Раскладку C++-структуры задаёт Clang, поэтому к типу иду через AST.
Нужные узлы --- \texttt{RecordDecl} и \texttt{FieldDecl}. Это ближе к задаче, чем
переписывание \texttt{getelementptr} в середине пайплайна.
Перестановка полей объекта --- решение фронтенда и ABI.

Тип не трогаю, если он в публичном заголовке, объявлен
\texttt{extern "C"}, адрес поля сохраняется, наружу торчит
\texttt{offsetof}, есть union, каст или сериализация всего объекта
через \texttt{memcpy}.

\end{ai}

Результат фазы: класс безопасных преобразований и его границы.
Чеклист отказа на одном своём типе. Тип, который чеклист пропускает,
идёт в фазу 4.

\subsubsection{Фаза 4. Носитель инструмента}

Выбираю, где живёт преобразование, и дочитываю только этот кусок
LLVM. Носители от простого к сложному.

\begin{ai}
\begin{enumerate}
    \item Отчёт: рекомендованный порядок полей и split, правки
    руками. На нём видно, безопасно ли преобразование.
    \item Clang-плагин на \texttt{RecordDecl} и \texttt{FieldDecl},
    при необходимости \texttt{Rewriter}. Для типов с internal
    linkage, поля которых не address-taken.
    \item LLVM-pass для структур, которые не убегают наружу. Тогда
    уже нужны IR памяти (\texttt{load}, \texttt{store},
    \texttt{getelementptr}, \texttt{StructType}), запуск через
    \texttt{opt} или \texttt{clang -fpass-plugin}, различие analysis
    pass и transform pass. Подсчёт \texttt{load} и \texttt{store}
    профиль памяти не заменяет: это только способ убедиться, что
    плагин запускается. Книги LLVM Essentials и Getting Started with
    LLVM Core Libraries не беру: API там старый. Новый Pass Manager
    описан в Writing an LLVM Pass,
    \url{https://llvm.org/docs/WritingAnLLVMNewPMPass.html}.
\end{enumerate}

Проход компилятора пишу, если отчёта и правки AST мало.

Placement объектов делаю через hot/cold hint на аллокацию: LLVM
MemProf и \texttt{operator new} с hot/cold в tcmalloc. Hint помечает
объект целиком, не поле, поэтому reorder и split им не заменяются.
Свой аллокатор или арена --- если hint не раскладывает горячие и
холодные объекты по разным областям. Pass для placement не нужен.

Порядок внутри фазы: сначала reorder с тем же alignment и тестом,
что значения на выходе совпали. Split вторым. Placement третьим.
\end{ai}

Результат фазы: одно преобразование на одном закрытом типе,
программа считает то же самое.

\subsubsection{Изменения порядка полей по стандарту}
По стандарту языка Си перестановка полей компилятором категорически запрещается,
так как порядок строго соответствует объявлению. Возможен только автоматический
отступ. В C++ перестановка также запрещается, в частности для Plaid Old Data или
же Standard-layout. Все классы являются Standard-layout, если они не имеются следующего:

\begin{enumerate}
    \item Разные уровни видимости переменных, 
    \item Наличие виртуальных функций, 
    \item Есть множественное наследование при условии, что и 
        у базового, и у дочернего класса есть нестатические поля.
\end{enumerate}

Если хотя бы одно из этих требований не соответствует, то класс перестает быть
"Standard-layout" и становится "non-standart-layout". Однако даже в этом случае
компилятор всё равно не имеет права произвольно перещать отдельные переменные,
объявленные внутри одной секции доступа. То есть стандарт разрешает:
\begin{enumerate}
    \item Перестановка целиком секций доступа. То есть выбирать, помещать ли
        сначала private поля, либо помещать сначала public
    \item Размещение полей базовых классов. Если есть наследование, стандарт не регулирует, 
        где именно относительно друг друга будут лежать поля базовых классов и 
        поля класса-наследника.
    \item Компилятор сам решает, куда вставить указатель на таблицу виртуальных
        функций. 
\end{enumerate}

\textbf{Вывод:} реализация данного проекта нарушает стандарт C++ - увы.

\subsubsection{Application Binary Interface:}
ABI описывает, как уже скомпилированный код взаимодействует с другими бинарными
компонентами, то есть:
\begin{itemize}
    \item соглашения о вызовах функций;
    \item представление типов в памяти;
    \item размеры и выравнивания типов;
    \item смещение полей структур и классов;
    \item представление виртуальных функций и некоторых других языковых механизмов;
\end{itemize}

Главный принцип: если все части программы пересобираются вместе, многие изменения ABI 
допустимы — при условии, что программа не обязана сохранять старое двоичное представление 
объектов. Однако полной пересборки недостаточно, если расположение полей используется 
за пределами пересобираемого кода: например, в файлах на диске, в разделяемой 
памяти или в отдельно собранных расширениях.

\paragraph{Вывод}
Изменение расположения полей структуры может нарушить ABI, если другие компоненты продолжают использовать прежнее двоичное представление объекта. Однако для продукта, который собирается целиком, это ограничение не является абсолютным: если все зависимые компоненты пересобираются согласованно, а расположение полей не закреплено внешними интерфейсами или форматами данных, преобразование может быть допустимым.

Следовательно, при разработке инструмента необходимо определять, какие типы можно преобразовывать без нарушения совместимости. Для этого следует учитывать область использования типа, возможность его независимого использования другими компонентами, а также операции, зависящие от расположения полей. Если безопасность преобразования не удаётся установить, тип следует исключить из автоматической оптимизации.

\subsubsection{Остальные ограничения}
Осталось рассмотреть другие проблематичные случаи, а именно:
\begin{enumerate}
    \item Взятие адреса,
    \item Использование offsetof,
    \item Использования преобразования,
    \item использования преобразования
\end{enumerate}

Взятие адресов само по себе не запрещает перестановку полей. Если инструмент
изменит структуру и пересоберет всю программу, то указатель \&Obj.field вернёт
новый адрес. Однако могут возникнуть и проблемы, когда программа начинает ходить
по структуре с помощью арифметики с указателями. Например, если написать:
\begin{lstlisting}
 int* ptr = &obj.a;
 int* next = ptr + 1;
\end{lstlisting}

То при reordering возникнет ошибка, так как в данном коде next ожидается в
структуре сразу после ptr. 

\hrulefill

Конструкция \textbf{offsetof} позволяет получить смещение поля в
байтах относительно начала объекта. Выглядит код следующим образом:
\begin{lstlisting}
struct Data {
    int a;
    int b;
};

constexpr size_t offset = offsetof(Data, b);
\end{lstlisting}


Проблема аналогична взятию адреса. Если результат используется за пределами
исходного кода или фиксируется в другом месте. Собственно \textbf{cast} имеют
ровно ту же самую проблему. 

Копирование и сериализация через memcpy тоже опасна, так как memcpy позволяет
копировать какое-то количество байт из одной области памяти в другую. Если
где-то есть зависимость от старых данных и сделано что-то подобное:
\begin{lstlisting}
    std::byte buffer[sizeof(Data)];

    std::memcpy(buffer, &src, sizeof(Data));
\end{lstlisting}

и потом:
\begin{lstlisting}
    write(fd, buffer, sizeof(Data));
\end{lstlisting}, 
то есть запись этих байтов в файл. Тогда расположение полец становится частью
формата данных. В случае, если структура изменится, то программа может начать
записывать данные в другом порядке. Старые файлы при этом могут оказаться
несовместимыми с новой версией программы. Аналогично, если объектное
представление передается по сети или передается через Shared Memory другому процессу. 


\paragraph{Вывод}
Действительно, есть множество ограничений, которые в будущем стоит очень
тщательно изучить, а если более точнее, то как именно с ними бороться. Все они
исходят в целом из одного принципа - где-то сохранился плагин или прежняя версия
кода, которая обращается к old версии структуры после её splitting или reordering.

\subsection{Константин Владимиров: LLVM}

Данная лекция была вводной в LLVM IR, а именно: SSA представление, работа с
памятью, некоторые оптимизации. Так как проект предполагается быть осуществлен в
виде оптимизации в LLVM, то необходимо эту тему рассмотреть в начале. Сюда я
выделил всё, что связано с работой с памятью, так как может помочь в будущем.

Любая коммуникация с данными осуществляется через операции "store" и "load" по
указателю, так как все переменные на самом деле хранят не само значение поля, а
указатель на него. Память в LLVM — это просто плоский массив байт. Нельзя сказать "дай
мне значение переменной x". Можно только сказать "загрузи значение по адресу, 
который лежит в указателе POINTER" (инструкция load). Именно для этого getelementptr 
и нужен, так как он вычисляет эти адреса.

Таким образом можно анализировать GEP инструкции в купе со store/load 
в LLVM для нахождения hot/cold частей структур. 

Отдельное важное уточнение - \textbf{alloca}.
\begin{lstlisting}
    %ptr = alloca i32, align 4
\end{lstlisting}

Живет на стеке. Можно перезаписывать через store. Медленнее, но позволяет брать
адрес и менять значение. Это важно, потому что \textbf{текущий проект} анализирует 
memory access patterns. alloca — это источник указателей для большинства load/store.

Если есть код:
\begin{lstlisting}
%ptr = alloca %struct.S
%field = getelementptr %struct.S, %struct.S* %ptr, i32 0, i32 2
store float 1.0, float* %field
\end{lstlisting}

То понятно, что это локальная структура на стеке, и мы пишем в её третье поле. Такие
обращения очень быстрые (стек горячий), но они всё равно занимают cache lines.
Если структура большая, а используется только одно поле — это проблема.

В LLVM есть отдельная оптимизация - mem2reg, который удаляет alloca, если может доказать,
что:

\begin{itemize}
    \item Адрес переменной не уходит за пределы функции.
    \item Нет сложного алиасинга.
\end{itemize}

После mem2reg все load/store заменяются на SSA-значения и phi-узлы. Если нужно анализировать
IR, то это необходимо до mem2reg (или отключать его), потому что именно там видны реальные обращения к памяти. После mem2reg от структуры данных останутся только абстрактные регистры,
и нельзя будет понять, какие поля были горячими.

Последний важный пункт, который я хотел бы подчеркнуть из лекции - оптимизации в
LLVM. LLVM 11 делает более 100 высокоуровневых оптимизаций. Это огромное
количество. Каждая оптимизация — это отдельный проход, который преобразует IR.
Эти оптимизации называются \textbf{Pass Pipeline}. Благодаря определенным
параметрам можно посмотреть иерархически, какие оптимизации когда применяются, а
также посмотреть IR до конкретной оптимизации и после.

\subsubsection{Вывод для проекта:}

\begin{itemize}
    \item Для анализа вручную горячих мест, если понадобится, необходимо исследовать 
        alloca, store, load. 
    \item Мой проход должен входить в LLVM иерархию и быть зарегистрированным через 
        -fpass-plugin.
    \item Надо отчетливо понимать, где конкретно в конвейере должна быть моя
        оптимизация.
\end{itemize}

\subsection{Cache-Conscious Structure Definition}

Данное учение является центральным для данного проекта, потому что рассказывает
непосредственно о том, как данные внутри структур можно разбивать. Есть
несколько основных подходов:

\begin{enumerate}
    \item structure splitting;
    \item field reordering.
\end{enumerate}

Надо понимать, что данная статья является продолжением изучения темы об
улучшении производительности, где были исследованы методы оптимизацию кэша за счет
изменения расположения отдельных экземпляров структур в памяти, а не их внутреннего
устройства. Ключевая идея этих методов — co-location, где объекты пытаются
разместить в одном кэш-блоке, если они часто используются вместо. Это статья
считается продолжением этих исследований, но для больших объектов, где нельзя
просто взять и разместить несколько объектов в одном кэше, потому что размеры
кэша ограничены.

Мы рассматриваем, как можно переупорядочить содержимое структуры так, чтобы
больше полезных данных попадало в кэш для уменьшения cache-misses.

\subsubsection{Метод Splitting}

Один из способов splitting - разделить класс на hot и cold части, основываясь на
профилировании, а именно - как часто обращались к полям в классе. Благодаря
splitting можно поместить больше hot частей в cache block. 

Сразу с \textbf{проблем:} дополнительный указатель (занимает место), более медленный cold
path, расширение кода, больше объектов в памяти и т.д.. Кроме того, при не
репрезентативной входной нагрузке результаты могут быть искажены. 

Идея splitting'а применяется к классам, обращение к котором происходит
достаточно часто, из-за чего придумана формула:
\[
    A_i = \frac{LS}{100 * C}
\]
Где:
\begin{enumerate}
    \item LS — общее количество обращений к полям во всей программе;
    \item C — общее количество классов, к полям которых была хоть одна попытка
        обращения;
    \item $$A_i$$ — общее количество обращений к полям конкретного класса i;
\end{enumerate}

Таким образом, класс должен набрать хотя бы 1\% от среднего количества обращений по всем 
классам, чтобы считаться важным. Также класс должен иметь хотя бы 2 поля и быть
больше 8 байт.

После чего необходимо разделить класс на Hot и Cold части, используя \textbf{Агрессивный 
подход}:
\begin{enumerate}
    \item Правило: Поле помечается как «холодное», если к нему обращались не чаще, чем 
        $\frac{A_i}{2 * F_i}$ раз. 
        \begin{itemize}
            \item $F_i$ - количество полей в классе i. (То есть, если к полю обращаются в
                            два раза реже среднего по классу, оно отправляется в холод).
        \end{itemize}
    \item Проверка целесообразности: После этого алгоритм проверяет, достаточно ли велика
        получилась холодная часть. Она должна быть не менее 8 байт, чтобы окупить 
        затраты на создание и хранение ссылки на нее.
    \item Уравновешивание слишком агрессивного разделения: так как агрессивный
        подход может навредить в случае, если мы слишком много данных отправили
        в cold часть, и теперь приходится часто ходить по ссылкам, вводится формула:
        \[
            \frac{\max(hot(class_i)) - 2 * \Sigma cold(class_i)}{\max(hot(class_i))} > 0.5
        \]
        , где:
        \begin{itemize}
            \item max(hot) — количество обращений к самому горячему полю.
            \item $\Sigma$ cold — сумма обращений ко всем холодным полям.
        \end{itemize}
\end{enumerate}


\textbf{Реализация в Vortex:}
Чуваки запатчили Vortex компилятор и:
\begin{enumerate}
    \item \textit{Создали Cold Path.} Все поля, которые были помечены как "COLD" 
         вырезаются из исходного класса, для которых создался еще один класс
        "PREVNAME\_OLD". Учитывается, что новый класс наследуется только от
        базового класса OBJECT и не содержит никаких методов, кроме
        конструктора. В новые класс был добавлен указатель на COLD Path
    \item \textit{Изменение горячего класса.} Так как в классе могли быть
        private и Protected поля, то их нельзя просто вырезать. Таким образом
        они были перенесены в другой класс с видимостью public. Таким 
    \item \textit{Изменение обращения кода к переменным.} Если было обращение к
        COLD path, то компилятор превращает это в HOT.COLD.field путь, то есть
        делая двойную косвенность. Также конструктор горячего класса должен в
        первую очередь создавать объект холодного класса.
\end{enumerate}

\textit{Проблемы в подходе:}
\begin{enumerate}
    \item Для проблемы с сериализацией надо оценить прирост производительности.
        Если он достаточен, то можно явно делать конвертер.
\end{enumerate}

\subsection{Требования к проекту}
Основная цель работы заключается в исследовании возможности повышения производительности 
программы за счёт изменения размещения данных в памяти. При этом переупорядочивание полей 
структур, разделение горячих и холодных полей и 
изменение  размещения экземпляров объектов в рамках проекта рассматриваются 
как средства достижения этой цели, а не самоцель.


Для отбора репозитория я выделил следующие требования:
\begin{itemize}
    \item \textbf{Значительная кодовая база}.\\ 
        Проект должен содержать собственную реализацию алгоритмов и структур данных на C++,
        а не сводиться преимущественно к обвязке над библиотеками, реализованными на 
        других языках. Это нужно, чтобы исследуемые преобразования затрагивали существенные 
        части программы, а не только вспомогательный код.

    \item \textbf{Интенсивная обработка объектов в памяти}.\\
        Программа должна содержать горячие участки кода, в которых многократно
        обарюатываются пользовательские типы. Это могут быть массивы объектов,
        индексные структуры, деревья, графы или прочик структуры данных. 

    \item \textbf{Потенциально неоптимальная раскладка объектов}. 
        В проекте должны присутствовать пользовательский типы данных - классы и
        структры, для которых видна
        потенциальная возможность улучшить локальность данных или, другими
        словами, пространственную локальность. Например, горячий путь может часто 
        обращаться лишь к нескольким полям объекта, тогда как остальные поля используются 
        значительно реже. В результате при обращении к горячим данным могут загружаться 
        также крайне редко используемые
        данные, заполняя мусором cache line. Другой возможный случай - совместно 
        обрабатываемые объекты, экземпляры 
        которых размещены в памяти далеко друг от друга. Наличие подобных ситуаций 
        необходимо подтверждать, поскольку размер структуры 
        и количество её полей сами по себе не говорят о неэффективной раскладке.
        (например bbcache из статьи cache-conscious).

    \item \textbf{Воспроизводимость эксперимента.}\\
    Должна существовать возможность задавать фиксированные входные данные и
    получать детерменированный и повторяемый результат выполнения программы,
    зафиксировав идентичную конфигурацию сборки и запуска, а также достигая
    проверки корректности

    \item \textbf{Возможность безопасного преобразования.}\\
    В проекте должны присутствовать типы, для которых можно обосновать безопасность хотя бы 
    одного из исследуемых преобразований. Изменение раскладки не должно нарушать семантику 
    программы, требования ABI и другие контракты, от которых зависит корректность 
    выполнения. При этом ограничения необходимо оценивать отдельно для каждого типа и вида 
    преобразования: невозможность безопасно переупорядочить поля не обязательно исключает 
    возможность изменить размещение экземпляров объектов.

\end{itemize}

Перечисленные мною требования позволяют предварительно отобрать проекты, пригодные для 
высокоуровневого отбора и фильтрации репозиториев. Однако соответствие им еще не
гарантирует, что в выбранном проекте найдутся структуры, оптимизация которых
даст ощутимый и измеримый эффект. Именно поэтому я предлагаю ввести
макропризнаки на уровне исходного кода и профиля выполнений.

\paragraph{Признаки кода}

Выделены следующие признаки потенциально полезных для оптимизации участков:

\begin{enumerate}
    \item \textbf{Многократная обработка экземпляров одного типа.}\\
    Экземпляры одного пользовательского типа должны многократно обрабатываться в горячих 
    участках программы. Это условие необходимо, поскольку даже небольшое улучшение 
    стоимости обработки объекта может оказать заметное влияние на итоговую 
    производительность при большом числе повторений.

    \item \textbf{Неравномерное использование полей структуры.}\\
    Частота обращений к полям одного типа может существенно различаться: некоторые поля 
    используются практически при каждой обработке объекта, тогда как другие востребованы 
    лишь в отдельных сценариях. Потенциал для \textit{reordering} и \textit{splitting} 
    возникает в том случае, если существующая раскладка приводит к переносу лишних 
    данных при обращении к горячим полям. При оценке необходимо каким-то образом 
    учитывать размеры полей, а также их смещения относительно границ cache line и 
    фактический характер обращений к памяти.

    \item \textbf{Совместное использование разнесённых объектов.}\\
    В горячих участках программы могут последовательно или совместно обрабатываться 
    связанные объекты, расположенные в разных cache lines или на разных страницах памяти.
    Если такое размещение увеличивает затраты на доступ к данным, изменение взаимного 
    расположения экземпляров может улучшить пространственную локальность и уменьшить объём 
    задействованных cache lines или страниц. 

\end{enumerate}

\subsection{Сравнительный анализ проектов для профилирования}

Выбор проекта является существенной
частью исследования: даже корректно реализованный инструмент профилирования и
преобразования структур данных не позволит получить содержательные результаты,
если тестируемая программа не содержит подходящих объектов, не обладает
воспроизводимой нагрузкой или не позволяет проверить сохранение семантики после
изменения расположения данных.

В рамках работы рассматриваются три проекта: LLVM, QuickFIX и CppTrader.

Далее я опишу каждый из этих проектов, в котором попытаюсь охватить по
поверхностному research:

\begin{itemize}
    \item Что из себя представляет проект
    \item К каким структурам идет постоянное обращение
\end{itemize}

\subsubsection{Проект LLVM}

\textbf{LLVM} представляет собой промежуточное представление программы, оптимизаторы,
генераторы машинного кода и различные инструменты разработки.

Этот проект первый пришел в голову, так как в IR постоянно приходится прыгать по
инструкциям, BasicBlock и другим структурам, что даёт потенциал для последующей
оптимизации.

Можно выделить несколько характерных типов:

\begin{itemize}
    \item \texttt{llvm::Instruction} - представление инструкции IR; 
    \item \texttt{llvm::BasicBlock} - представление базового блока, содержащего 
        llvm:Instruction;
    \item \texttt{llvm::Function} - представление функции;
    \item контейнеры \texttt{DenseMap} и \texttt{SmallVector}, широко используемые
    в различных подсистемах LLVM.
\end{itemize}


С точки зрения исследуемой задачи LLVM обладает несколькими преимуществами. Во-первых, 
проект содержит множество алгоритмов, которые многократно обходят
графы, списки и таблицы объектов. Это создаёт потенциально интересную среду
для исследования пространственной локальности и поведения кэш-памяти.

Во-вторых, LLVM располагает системой проходов, анализами 
указателей и механизмами межпроцедурной оптимизации. Досточно удобно для
проведения тестового сценария и детерменированного воспроизведения.

\textbf{Однако} масштаб и сложность LLVM одновременно создают действительно большие 
трудности в рамках дипломного исследовательского проекта.

Объекты инфраструктуры тесно связаны между собой: инструкции принадлежат
базовым блокам, базовые блоки связаны с функциями, а многие структуры
используют указатели, intrusive-контейнеры и специализированные аллокаторы.
Изменение расположения полей может затронуть большое количество участков
кода, а изменение размещения объектов способно повлиять на существующие
механизмы управления временем жизни и владением. Это несет достаточно большие
потенциальные риски, так как даже маленький изолированный модуль будет иметь
огромную сложность при оптимизации. При непосредственной разработке проекта это
объективно большой минус.

Кроме того, LLVM представляет собой инфраструктурный проект с большим
количеством публичных интерфейсов. Для отдельных типов необходимо учитывать
совместимость ABI, внешнюю видимость, использование объектов сторонними
компонентами и ограничения, возникающие из-за сохранения адресов объектов. Это
всё ложится в рамки проекта, но опять же несет слишком большую сложность для
первоначальной разработки.

Таким образом, LLVM является хорошим кандидатом, но в качестве первого проекта для 
экспериментальной проверки он представляет повышенную сложность: трудно изолировать влияние
изменения расположения данных от остальных факторов.

\subsubsection{Проект QuickFIX}

\textbf{QuickFIX} представляет собой реализацию движка протокола FIX - 
Financial Information eXchange, предназначенного для обмена финансовыми
сообщениями между торговыми системами с помощью FIX-сообщений. 

Важной частью реализации является модель представления FIX-сообщения.
можно выделить следующие структуры:

\begin{itemize}
    \item \texttt{FieldBase} - базовое представление поля FIX-сообщения;
    \item \texttt{FieldMap} - контейнер для хранения и организации полей;
    \item \texttt{Message} - представление сообщения, включающее заголовок,
    тело и завершающую часть.
\end{itemize}

Так как данным типом \texttt{FieldBase} постоянно оперирует программа, 
а внутри структуры хранится
идентификатор, строковое представление, стрпуктура метрик и прочие поля, то это
уже говорит о потенциале для оптимизаций. \underline{При этом важно подчеркнуть}, 
что конкретное разделение полей
\texttt{FieldBase} на горячие и холодные заранее не установлено. Например,
строковое представление может активно использоваться при сериализации,
но это не означает, что оно будет одинаково востребовано во всех сценариях. Это
усложняет оптимизацию, потому что вполне вероятно сложно будет выделить какую-то
корректную нагрузку на программу под общий сценарий.

Контейнер \texttt{FieldMap} хранит поля в
std::vector<FieldBase> с использованием специализированного
аллокатора. Для повторяющихся групп используется отдельная структура
на основе std::map, значения которой содержат векторы указателей
на другие объекты \texttt{FieldMap}.

Однако QuickFIX имеет и ограничения с точки зрения поставленной задачи.

Основная работа с данными сосредоточена вокруг обработки сообщений и их
полей. Это делает проект подходящим для исследования расположения полей
внутри отдельных объектов и, в некоторой степени, разделения горячих и
холодных данных. Вместе с тем сценарии размещения большого количества
взаимосвязанных объектов в куче представлены не разнообразно, чем
в системе, непосредственно реализующей обработку биржевого стакана
и потока заявок.

Кроме того, \texttt{FieldMap} использует стандартные контейнеры и
специализированные аллокаторы. Поэтому при оценке результатов необходимо
разделять эффект изменения layout самих объектов и эффект работы
контейнеров и аллокатора.

Таким образом, QuickFIX не считается подходящим проектом для тестирования.


\subsubsection{Проект CppTrader}

\textbf{CppTrader} - библиотека компонентов для построения торговых
платформ. В отличие от QuickFIX, который в первую очередь решает задачу обработки
протокольных сообщений, CppTrader непосредственно реализует структуры
и алгоритмы, необходимые для управления заявками и состоянием биржевого
стакана.

В реализации менеджера рынка \texttt{MarketManager} используются
следующие контейнеры:

\begin{itemize}
    \item \texttt{std::vector<Symbol*>} для хранения символов;
    \item \texttt{std::vector<OrderBook*>} для хранения биржевых стаканов;
    \item \texttt{CppCommon::HashMap<uint64\_t, OrderNode*>} для хранения
    заявок по их идентификаторам.
\end{itemize}

После каждого события MarketManager должен обновить внутреннее состояние рынка.
Требуется быстро оперировать с заявки, работать с ценой, поддерживать лучшие
уровни и т.д.. Из-за этого разработчики приняли решение использовать менеджеры
памяти, то есть pool allocator. Они сделаны для разных категорий, вот их пример:

\begin{itemize}
    \item \texttt{LevelNode} - узлы уровней цен;
    \item \texttt{Symbol} - торговые инструменты;
    \item \texttt{OrderBook} - биржевые стаканы;
    \item \texttt{OrderNode} - узлы заявок.
\end{itemize}

Для этих типов объявлены отдельные экземпляры
\texttt{PoolMemoryManager} и \texttt{PoolAllocator}.
Следовательно, проект уже содержит специализированную инфраструктуру
выделения памяти, которую можно исследовать в контексте оптимизации
размещения объектов.

В отличие от ситуации, когда все объекты создаются через стандартный
аллокатор, здесь можно исследовать, насколько существующие пулы уже
обеспечивают пространственную локальность и остаётся ли дополнительный
потенциал для улучшения размещения объектов.

При этом нельзя заранее утверждать, что существующая реализация
неэффективна. Напротив, наличие пулов может означать, что часть проблем
локальности уже решена.

Ещё одним преимуществом CppTrader является наличие воспроизводимого
сценария обработки исторических данных NASDAQ ITCH. В README проекта
приведён пример запуска benchmark на сценарии, где указано
283 миллиона обработанных ITCH-сообщения и 631 миллиона обновлений
состояния рынка. Проект предоставляет
фиксированный входной набор данных и достаточно продолжительную нагрузку,
позволяющую собирать аппаратные профили.


\subsubsection{Общий вывод}


Итоговый выбор я оставил за \textbf{CppTrader}, так
как он сочетает несколько важных для исследования
характеристик. Проект содержит собственные структуры для управления
заявками и биржевыми стаканами, активно использует указатели
и специализированные пулы памяти, а также предоставляет
воспроизводимый сценарий обработки большого набора исторических
биржевых сообщений.

При этом выбор CppTrader не означает, что все его структуры
обязательно нуждаются в оптимизации. Перед выполнением каких-либо
преобразований необходимо провести предварительное исследование
исходного кода и аппаратное профилирование.

\subsection{Последующие шаги для профилирования}

В самом репозитории проекта есть штатный бенчмарк
\texttt{cpptrader-\allowbreak performance-\allowbreak market\_\allowbreak manager}.
Он читает запись NASDAQ ITCH
и по сообщениям обновляет состояние стаканов. На этом сценарии я хочу
найти хотя бы один горячий участок, где текущая раскладка полей или
размещение объектов увеличивает число затрагиваемых кэш-линий или страниц.

Общая цель тестирования заключена следующими пунктами:
\begin{enumerate}
    \item \textbf{Зафиксировать исходные замеры.}
    Собрать CppTrader на Linux и несколько раз прогнать бенчмарк на одном
    фрагменте NASDAQ ITCH. Записать пропускную способность, циклы на
    обновление и доступные счётчики промахов LLC и dTLB.

    \item \textbf{Найти горячие чтения.}
    Снять CPU-профиль и профиль чтений памяти. По адресам и времени сэмплов
    связать обращения с конкретными полями \texttt{OrderNode} или
    \texttt{LevelNode}, в зависимости от того, куда укажет профиль.

    \item \textbf{Проверить одно изменение.}
    Выбрать перестановку полей или новое размещение узлов, которое может
    сократить число затрагиваемых кэш-линий или страниц. Проверить тестами
    и по состоянию стаканов, что обработка осталась корректной, затем
    повторить замеры и сравнить эффект с исходным разбросом.
\end{enumerate}

Если первый фрагмент не даст кандидата на оптимизацию, план предусматривает
повторить профилирование на другом фрагменте с активными обновлениями стакана.

Более подобный план для достижения подобных этапов:

\begin{enumerate}
    \item \textbf{Зафиксировать исходный прогон.}
    Соберу CppTrader на машине с нативным Linux, включив оптимизации
    и отладочную информацию. необходимо записать коммит, версию компилятора, флаги
    сборки, модель CPU и версию ядра.
    Для пробных запусков стоить взять один и тот же фрагмент распакованного ITCH
    с начала файла, обрезанный по границе сообщения. Проверю, что бенчмарк
    выдаёт одинаковое число сообщений и обновлений и завершает обработку
    без ошибок. После прогрева файлового кэша начну с пяти прогонов на одном
    ядре. Из вывода бенчмарка возьму пропускную способность, а через
    \texttt{perf stat} сниму циклы и доступные счётчики промахов LLC и dTLB.
    Аппаратные счётчики пересчитать нужно на одно обновление. Если короткий 
    фрагмент даёт мало обновлений
    или нестабильные результаты, увеличу его.

    \item \textbf{Найти горячие обращения к памяти.}
    На том же входном фрагменте сниму два профиля. По CPU-профилю
    (\texttt{perf record}) оценю, какая доля сэмплов приходится на обновление
    стаканов и поиск заявок в \texttt{MarketManager}, а какая - на разбор
    ITCH и чтение файла. Профиль чтений (\texttt{perf mem}) покажет, на какие
    инструкции в этих участках приходится больше всего сэмплов обращений
    к памяти.

    Перед записью профиля чтений проверю доступные
    аппаратные события командой \texttt{perf mem record -e list}. 
    Затем сделаю короткий прогон с
    \texttt{perf mem -t load record -U} и проверю, что в выводе
    \texttt{perf script} есть и адрес инструкции, и виртуальный адрес
    данных. Для основного прогона запишу выбранное событие и порог задержки,
    если он применяется.

    \item \textbf{Связать обращения с полями объектов.}
    Тип объектов для анализа нужно выбрать по профилю. Если среди горячих операций
    окажутся поиск и обновление заявок, начну с \texttt{OrderNode}. Если
    профиль укажет на операции с ценовыми уровнями, рассмотрю
    \texttt{LevelNode}.

    В отдельной сборке добавлю журнал выделения и освобождения узлов
    выбранного типа. Для каждого узла запишу адрес, размер и время этих
    событий. Временные отметки журнала и профиля одного прогона приведу
    к общей шкале. Тогда по адресу данных и времени сэмпла смогу определить,
    какой экземпляр занимал этот участок памяти в момент обращения, даже
    если пул использовал один слот несколько раз. По смещению от начала
    объекта и отладочной информации DWARF определю поле. Подсчитаю долю
    сопоставленных сэмплов, распределение по полям и число кэш-линий,
    на которые пришлись обращения.

    \item \textbf{Оценить раскладку полей и размещение объектов.}
    По примеру \texttt{bbcache} посмотрю, какие поля одного объекта читаются
    близко по времени. Если аппаратных сэмплов для этого окажется мало,
    запишу последовательность обращений на одном горячем пути, например
    при поиске и обновлении заявки. С учётом размеров и выравнивания полей
    проверю, можно ли разместить поля, которые читаются вместе, в меньшем
    числе кэш-линий. Для связанных узлов подсчитаю, сколько кэш-линий
    и страниц затрагивают обращения при текущем размещении в пулах.

    \item \textbf{Проверить изменение и принять решение по CppTrader.}
    Если исходные замеры воспроизводятся, а профиль показывает, что
    конкретное изменение может улучшить локальность, внесу его с учётом
    ABI и времени жизни объектов. Запущу тесты проекта и сравню состояние
    стаканов в контрольных точках на том же входе. Затем повторю замеры
    без журналирования и проверю, выходит ли разница в метриках за пределы
    разброса исходных замеров. Воспроизводимые замеры и обоснованное
    изменение станут основанием продолжить эксперименты на CppTrader.

\paragraph{Подведу итог, что я сделал}
Так как CppTrader является библиотекой компонентов, то для тестирования есть
исполняемые файлы типа \textbf{cpptrader-performance-market\_manage}, которые

С помощью них мы и будем смотреть циклы процессора, L3 и dTLB. По этим данным можно понять,

\paragraph{Изоляция cpu-1 от context switch}

Я понял, что недостаточно считать perf stat, так как переключения контекста и

\begin{verbatim}
    isolcpus=domain,managed_irq,1 nohz_full=1 irqaffinity=0,2-15

\begin{itemize}
    \item убирает CPU 1 из обычной балансировки задач и по возможности

    \item позволяет ядру отключить тик, при котором выполняется одна подходящая задача

\subsubsection{Нахождение сосредочения сэмплов}
После perf recode можно понять, какие части какие части CppTrader занимают больше всего 
процессорных циклов в пользовательском режиме. Таким образом можно выделить
домены приложения для последующего изучения. Результатом будет список горячих
функций и стеков вызовов с их долями в профиле. После чего переходим к причинам
затрат в следующих шагах.

После снятия профиля чтений на основе perf mem можно узнать, какие инструкции
обращаются к памяти на выбранных путях. По итогу получится список инструкций с
большим числов сэмплов чтений. Адрес инструкции покажет, кто выполнил чтение, а
адрес данных - откуда прочитали. Время сэмпла позволит понять, какой объект
находился тогда по этому адресу

После получения инструкций необходимо сопоставить адреса с объектами, чтобы
получить распределение сопоставленных чтений по полям выбранного типа и доля
сэмплов, которую удалось сопоставить. Это покажет, какие поля стоит исследовать
вместе.

\underline{Анализ раскладки}. Наконец необходимо понять, можем ли мы сократить
число кэш линий или страниц, затрагиваемых одной гоорячей операцией.
Проверяем, читаются ли определённые поля вместе и уменьшит ли их сближение число 
затрагиваемых кэш-линий. Затем выясняем, при каких условиях перестановка безопасна с 
учётом ABI и наблюдаемости раскладки.

После чего стоит попробовать ручное изменение, то есть проверить гипотезу перед
реализацией в LLVM. Ручной вариант дает некий результат, по которому можно
понять, поможет ли автоматическая реализация в LLVM улучшить оптимизацию.

\paragraph{Снятие CPU-профиля}

Снятие CPU профиля происходило командой:
\begin{lstlisting}
taskset -c 0 perf record --user-callchains --sample-cpu \
    -e cpu_core/cycles/u -c "$period" --call-graph dwarf -o "$profile" \
    -- taskset -c 1 "$benchmark" < "$input"
\end{lstlisting}

Изначально были найдены утери сэмплов в \textbf{perf}. Это связано с тем, что при 
каждых 100'000 или 50'000 пользовательских циклов срабатывает прерывание, при
котором ядро складывает запись в кольцевой буфер в памяти. Пользовательский
процесс perf record читает записи из этого буфера и сохраняет их в perf.data.
Однако если новые записи поступают быстрее, чем perf record успевает освобождать
место, буфер может заполниться. Тогда ядро пропускает запись и сообщает о
потере.

ПО итогу пришлось процесс \texttt{perf record} привязать к CPU~0, а бенчмарк - к
изолированному CPU~1 с заданными пределами частоты 3300~МГц. Таким образом
получится параллельно вычитывать сэмплы их кольцевого буфера.

записано 545--600 сэмплов при периоде 100\,000 и 952--1152 при
